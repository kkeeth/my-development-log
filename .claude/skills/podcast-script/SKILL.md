# 台本の執筆

**この台本は「完パケ」で書く．** 収録時に読み上げるだけで成立する状態にすること．
話し言葉・冗談・個人的なエピソードまで含めて書き切る．
「※ここで補足」「（適宜エピソードを挿入）」のような**書き手への指示を本文に残さない**．

肉付けや補足が必要だと感じたら，**執筆中にユーザーへ質問する**．
本人しか知らないエピソード（過去の失敗，現場での実感，好み）は勝手に創作せず必ず聞く．

## 手順

### 1. 素材を揃える

- `src/PODCASTS/WEB小噺/SHOW_RULES.md` を読む（フォーマット・文体・尺・定型文）
- ネタと調査結果を用意する．無ければ `podcast-research` skill を先に回す
- ネタ帳は配信管理スプレッドシートの **「企画ストック（雨宿り）」** タブ．
  そこから採る場合は `メモ` 列の調査メモとソースも回収する

```bash
python3 .claude/skills/podcast-publish-log/scripts/sheets.py rows --tab "企画ストック（雨宿り）" --max 60
```
- 参考として最近の完成台本を 1〜2 本読む（`Season5/github-octocat-siblings.md` など）．
  **文体と語りのリズムは既存台本に合わせる．ただし長さは合わせない**
  （既存は 7〜20 分，現在の目標は 28〜30 分）

### 2. 構成を組む

**まず，構成より先に次の 2 行を埋める．埋まらないなら調査が足りない．**

```
焦点：{誰／どの事件}　← 1 回 1 焦点．2 つあるなら 2 回に割る
これは，{A}と{B}と{C}の話です．
```

- 「焦点」は原則**人**にする．主語がモノになる回は弱い（`SHOW_RULES.md`「第一関門」）
- 2 行目の A・B・C は「具体物」「大きい主題」「引っかかり」を 1 つずつ．
  これは**そのまま概要欄の第 2 段落になる**ので，喋り言葉として自然な形にしておく
- この 2 行は `## 🎙️ 収録メモ` の冒頭にも残す

そのうえで，話の流れを箇条書きで組み，ユーザーに見せて合意を取る．
**本題は次の 5 部構成を必ず守る．**

| 段 | 中身 | 目安 |
| --- | --- | --- |
| 1【つかみ】 | **シーンから入る**．場所・年・人のどれかを具体的に置く．そこから今日の問いを立てる | 2〜3 分 |
| 2【背景/歴史】 | そのモノ・言葉・人物が生まれた経緯 | 5〜7 分 |
| 3【メインの小噺・裏話】 | この回の核．「へー，そうなんだ」の本体 | 8〜10 分 |
| 4【意外な事実や補足】 | 寄り道の小ネタ，関連する別事例 | 6〜8 分 |
| 5【まとめ・締めのひとこと】 | 持ち帰れる一言．所感を入れるならここ | 2〜3 分 |

28〜30 分は山が 1 つでは持たない．**3 と 4 に山を 3〜4 つ**配分する．
各段に想定分数を振り，合計が 26〜28 分（本編）になるか確認する．
届かないなら，構成の段階でネタを足す．本文を書き始めてから水増しすると密度が落ちる．

構成が固まる前に本文を書き始めない．書き直しのコストが大きい．

この段階で，**本人にしか書けない部分を洗い出して質問する**
（関連する個人的な体験，現場での実感，好み）．完パケにするために必要な材料である．

### 3. 執筆する

`SHOW_RULES.md` の台本フォーマットに沿って `src/PODCASTS/WEB小噺/Season5/<slug>.md` を作る．

- オープニング・エンディングの**定型文は一字一句そのまま**貼る（タイトル部分だけ差し替え）
- 本文で触れた事実の出典は，本題の直後に `📎 URL` で全部並べる
- `## 🎙️ 収録メモ`（トーン／強調ポイント／尺／タグ）まで書いて完成とする

### 4. 尺と表記を確認する

**尺**

```bash
awk '/^### 本題/,/^### エンディング/' <file> | grep -v '📎' | tr -d '[:space:]' | wc -m
```

⚠️ **`📎` の行を必ず除外する．** 参考 URL は読み上げないため，含めると尺を過大に見積もる
（例：PHP 回は 8,961 字 → 実際に読む分は 8,432 字．約 1.7 分の差）．

300〜350 字/分で割り，目標の **28〜30 分**（本編 8,000〜9,800 字）に届いているか見る．

**足りないことのほうが多い**．その場合は水増しせず，掘る場所を提案してユーザーに相談する．
（人物の背景／関連する別事例／当時の時代背景／寄り道の小噺／Engineering HR 視点の所感）
オーバーしていれば削る候補を挙げる．

**句読点**

`、` と `。` が 1 つでも残っていたら直す．出力が空になるまで繰り返す．

```bash
grep -n '[、。]' <file>
```

既存台本にも混在が残っているので，参考にした文をそのまま引き写すと混入しやすい．

### 5. 納品ゲート（これを通るまで完成と言わない）

書き上げたら `### 本題` の中身を読み返し，次を全部確認する．
**1 つでも引っかかったら，それは台本ではなく構成メモである．書き直す．**

- [ ] 本題に `-` や `*` の**箇条書きが 1 行も無い**．すべて地の文で書かれている
- [ ] `【つかみ】`『【背景/歴史】』のような**構成ラベルが本文に残っていない**．
  5 部構成は守るが，ラベル自体は台本に書かず段落の流れで表現する
- [ ] 「〜という話をする」「〜を紹介する」のような**要約体が無い**．実際に喋る言葉そのもので書く
  （✕「ここで streak 文化を紹介」／○「2014 年 4 月 10 日，ジョン・レシグさんという方がブログを書きます」）
- [ ] 事実の羅列で終わる段落が無い．**そのつど本人の反応・所感が付いている**
- [ ] 専門用語は初出時にその場でかみ砕いている
- [ ] 上から音読して**そのまま収録が成立する**．口頭で補う必要のある箇所が無い
- [ ] 本題の文字数（📎 除く）が **8,000〜9,800 字**に入っている

完成形の参考は `Season5/php-creator-was-a-perl-user.md`，
`Season5/json-inventor-douglas-crockford.md`，
`Season5/why-github-stopped-counting-streaks.md` の 3 本．
**構成メモを箇条書きで置いて済ませるのは，この番組では納品物ではない．**

### 6. 後続を案内する

`src/SUMMARY.md` の PODCASTS セクションに 1 行追加したうえで，
`podcast-factcheck` → `podcast-review` → `podcast-meta` に進むことを伝える．

## 執筆ルール

### 絶対に守るもの

- **句読点は読点「，」，句点「．」**．`、` と `。` は使わない．
  執筆後に必ず検査する（下記「4. 尺と表記を確認する」）
- **オープニング・エンディングの定型文は一字一句変えない**（`SHOW_RULES.md` 参照）．
  差し替えるのはタイトル部分だけ
- **本題は 5 部構成**（つかみ／背景・歴史／メインの小噺・裏話／意外な事実や補足／まとめ）
- **📎 URL は本題の末尾**に 1 行 1 本で列挙
- **ファイル名は英語のハイフン区切り**（例：`why-is-cookie-called-cookie.md`）
- **保存先は `src/PODCASTS/WEB小噺/Season5/`**

### ネタの性質

- 蘊蓄・裏話・意外な事実・名前の由来など「**へー，そうなんだ**」ネタを優先する
- **技術的に踏み込みすぎない．** 一般的なエンジニアが聞いて分かるレベルに保つ．
  仕様の詳細やコードの話に降りていくと，この番組の持ち味から外れる

### 語り口

- 話し言葉（です・ます調），一人称は **僕**
- 耳だけで理解できる文にする．箇条書き前提の説明にしない
- 一文を長くしない．読点で延々つなぐと読み上げで息が続かない
- 専門用語は出したその場でかみ砕く
  - 例：「マージ，つまり複数人が書いた変更をひとつにまとめる作業ですね」
- 技術が濃くなる回は，本題に入る前に非エンジニア向けのことわりを入れる
- 「〜ですよね」「〜なんですよね」で同意を誘い，独り語りにしない．
  ただし**話者個人の感覚には付けない**．詳細は `SHOW_RULES.md`
- **主観は言い切る．**「〜と感じます」「〜と思います」．
  「〜と感じるんですよ」「〜と思うんですよ」のようにぼかさない
- **引用の導入フレーズを固定しない．** 「〜はこう言っています」の連続は AI が書いた文章に見える．
  「〜と仰っています」「〜が，こんな言い方をしてるんですよ」などを混ぜる（同じ導入は 1 本に 2 回まで）
- 「ちなみに」「面白いのが」で寄り道を挟むのがこの番組らしさ．ただし本筋を見失わせない
- **冗談や個人的なエピソードも本文に書き込む**（完パケにするため）．
  ただし本人しか知らない話は創作せず，必ず質問して聞き出す
- 終盤に **Engineering HR（技術広報・採用広報）視点の所感**を入れると厚みが出る（必須ではない）．
  技術そのものより「関わった人・組織・伝わり方」に寄った視点が持ち味
- 数字・固有名詞は読み下せる表記にする（「56 歳」「2026 年 4 月 4 日」）
- 事実として言い切れないことは「〜と言われています」に落とす．
  盛らない．盛った分は後段のファクトチェックで全部剥がされる

### ネタが行き詰まったとき

指定されたネタで 28〜30 分に届かない，または裏取りできず成立しないと判断したら，
**新ネタを 3〜5 本提案してレポートに載せる**．無理に薄い台本を書き上げない．
提案は `SHOW_RULES.md` の「ネタ選びの基準」に沿って，優先順位
（人物の決断・失敗・執念／裏話／名前の由来・語源／蘊蓄）から選ぶ．
