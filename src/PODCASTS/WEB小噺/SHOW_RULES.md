# 雨宿りと WEB の小噺 — 番組ルール

このファイルは podcast 系 skill / subagent すべての参照元（single source of truth）である．
台本の書き方を変えたいときは，skill ではなくこのファイルを直す．

## 番組概要

- **番組名**：雨宿りと WEB の小噺
- **パーソナリティ**：**気づきの配達屋** Keeth こと桑原（40 代の Engineering HR ／ DevHR．いわゆる技術広報・採用広報．
  Engineering Manager および経営ポジションの経験あり）
- **コンセプト**：Web テクノロジーの歴史や裏側にある，ちょっとした小噺
- **タグライン**：**Web の裏側には，必ず誰かがいる．その名前は，たいてい残っていない．**
- **想定リスナー**：Web エンジニア，または Web テクノロジーに興味のある非エンジニア
  - 立ち位置は「**詳しい人のための番組ではなく，気になった人のための番組**」．
    技術的な予備知識は要らない，と番組側から明示する．
    概要欄・トレーラー・初回オープニングでこの一文を出してよい
- **他番組との差別化**：技術史を語る番組は既にある（海外なら Advent of Computing，
  Found in the Machine，CoRecursive）．この番組の持ち場は
  **「技術そのもの」ではなく「その技術に賭けた人・組織・伝わり方」**である．
  Engineering HR という肩書きは他の誰も持っていない武器なので，そこに寄せる
- **配信基盤**：Art19（配信 URL は `https://art19.com/shows/kkeethengineers/episodes/<uuid>` 形式）
- **現在のシーズン**：Season5
- **ハッシュタグ**：`#WEB小噺`

## 尺の目安

- 目標は **28〜30 分**（ジングル・クロージングトークを含めた総尺）
- 内訳の目安：オープニング 30 秒〜1 分／本編 26〜28 分／クロージング 1 分
- 日本語の読み上げは **300〜350 字/分** で見積もる → 本編は **8,000〜9,800 字**
- ⚠️ **既存台本（Season4／Season5）は 7〜20 分と短い．長さの参考にしてはいけない．**
  文体・語りのリズムの参考にはする
- 30 分を 1 本の直線的な説明で持たせるのは無理がある．
  **山を 3〜4 つ**（意外な事実／人間のドラマ／寄り道の小噺）配置して緩急をつける
- 台本を書いたら必ず文字数を数え，尺に収まっているか確認する
- ⚠️ **下限に足りなくても水増ししない．** 収録時に雑談やアドリブが自然に入って伸びる前提なので，
  台本が 26〜27 分相当でも問題ない．尺を埋めるためだけに段落を足すと密度が落ちるだけである．
  足りないときに提案してよいのは「掘る価値のある場所の指名」までで，実際に埋めるかは本人が決める

## 文体

ブログ（`docs/BLOG_RULES.md`）とは別ルールなので混同しないこと．

| | ポッドキャスト | ブログ |
| --- | --- | --- |
| 文体 | です・ます調（話し言葉） | だ・である調 |
| 一人称 | **僕** | 私 |
| 句読点 | **，．**（全角カンマ・ピリオド） | ，． |

⚠️ **句読点は読点「，」，句点「．」．`、` と `。` は使わない．**
既存台本 34 本には `、。` が多数残っている（Season5 だけで 627 箇所）．
文体の参考に既存台本を読むと**そのまま引き写して混入する**ので，
書き上げたら必ず `grep -n '[、。]' <file>` で検査すること．

- **耳だけで理解できること**を最優先する．箇条書きや図表を前提にした説明をしない
- 専門用語は出したその場でかみ砕く
  - 例：「マージ，つまり複数人が書いた変更をひとつにまとめる作業のことですね」
- 技術の話が濃くなる回は，本題に入る前に一言ことわりを入れる
  - 例：「今回は途中からわりとガッツリめにエンジニア向けの話になります．専門用語もかみ砕くので，非エンジニアの方も気楽に聞いてください」
- 終盤に **Engineering HR（技術広報・採用広報）としての所感**を一段落入れると回に厚みが出る（必須ではない）
  - 「技術そのもの」より「その技術に関わった人・組織・伝わり方」に寄った視点が持ち味になる
  - 例：作った人の名前が語り継がれないこと，社内文化がプロダクトの顔に出ること，採用市場での見え方
- 「〜ですよね」「〜なんですよね」といった同意を誘う語尾を適度に混ぜ，独り語りにしない
  - ⚠️ ただし**話者個人の感覚に「ですよね」を付けない．** 同意しないリスナーがいる主観に使うと
    押しつけになる．使ってよいのは**事実**か**明らかな共通体験**に対してだけ
    - ✕「JSONってもう空気みたいな存在ですよね」（「いや違うやろ」と思うエンジニアがいる）
    - ○「JSONって，僕の中ではもう空気みたいな存在です」
- **主観は言い切る．** 自分の感覚を述べるとき，語尾をぼかして逃げない．
  「〜んですよ」「〜んですよね」で包むと，自信がないように聞こえる
  - ✕「〜と感じるんですよ」「〜と思うんですよ」「〜引っかかったんですよね」
  - ○「〜と感じます」「〜と感じることが多いです」「〜と思います」「〜引っかかりました」
  - 主観を**言い切る**のと，主観に**同意を求める**（「ですよね」）のは別物．
    前者はやる，後者はやらない
- **引用の導入フレーズを固定しない．** 「〜はこう言っています」ばかり続くと，
  読み上げたときに機械が並べたような単調さが出る．次のように散らす
  - 「〜はこう言っています」／「〜と仰っています」／「〜が，こんな言い方をしてるんですよ」
  - 「〜がこんなことを言い出すんですよ」／「〜はこう説明しています」／「〜と表現しています」
  - 同じ導入が 1 本の台本で 2 回を超えたら書き換える
- 数字・固有名詞は音で伝わる形にする（「56 歳」「2026 年 4 月 4 日」など読み下せる表記）

## 台本に書かないもの（収録時に本人が入れる）

台本は完パケで書くが，次のものは**あえて書かない**．収録しながら本人が自然に入れる．

- **前回回への言及・番組間のつなぎ**（「前回 PHP の回をやったんですけど」など）

したがって：

- 執筆時にこれらを書き足さない
- レビュー時に「内輪メタだ」「つなぎが無い」と減点しない．**意図的な欠落である**
- 尺の見積もりも，これらが乗って伸びる前提で見る

ただし**オチの先出しは別問題**なので，つなぎの中でも核心を明かす言い回しは台本から外す．
（例：「『発見しただけだ』と言い張った人の話です」を冒頭に置くと，本命の引用が効かなくなる）

## 参考リンク

- 本題の直後に `📎 URL` を 1 行 1 本で列挙する
- 本文で触れた事実の裏取りに使った URL は**すべて**残す．後段のファクトチェックがこれを起点にする
- 一次情報（公式ブログ，公式ドキュメント，本人のインタビュー，論文）を優先する
- **概要欄に出すときは素の URL ではなく書誌形式にする**．
  `著者名（発行年）「タイトル」媒体名. URL` の順．著者・年・媒体が入るだけで信頼性の見え方が変わる
  - 例：`Cunningham, W.（1992）「The WyCash Portfolio Management System」OOPSLA '92. https://...`
  - 個人ブログや本人ポストも同じ形式で書く．出せない要素（年が不明など）は省いてよい

## 回の設計：1 回 1 焦点

**1 回で扱う「人」または「事件」は 1 つに絞る．**
関連する話は寄り道として入れてよいが，焦点が 2 つある回は
「結局なんの話だったか」がリスナーに残らない．

回を書き始める前に，次の 2 行を埋める．埋まらないネタはまだ調査が足りない．

```
焦点：{誰／どの事件}
これは，{A}と{B}と{C}の話です．
```

2 行目は概要欄の第 2 段落にそのまま使う（後述）．
A・B・C は「具体物」「大きい主題」「引っかかり」を 1 つずつ置くと収まりがよい．

- 例：これは，**僕らが見落としている設備**と，**国家による大規模監視**と，
  **その装置がついに止まらなかったこと**の話です．

## タイトルの型

**一節で言い切る．`{フック}──{サブタイトル}` の二部構成は使わない．**

⚠️ **2026-09-02 に改訂．** 以前は海外の同ジャンル番組（Found in the Machine など）に倣って
`{フック}──{誰が何をしたか}` の二部構成を基本にしていたが，日本語のタイトル一覧で見ると
**「AI が作ったタイトル」に見える**という理由で外した．
タイトルの出来ではなく読み手側の AI 観の問題なので，その空気が落ち着いたら二部構成に戻す可能性がある．
それまでは一節で作る．

- **頭 20 字で勝負が決まる**．一覧・検索結果ではそこまでしか読まれない．
  エピソード番号 `{N}. ` で 3〜4 字使うので，**タイトル本体は 17 字前後**に引きを収める
- **引用・逆説・数字**のいずれかで意外性を出し，**体言止めか言い切り**で閉じる
- 節を割りたいときは `──` ではなく**全角カンマ `，`** を使う
- **人の気配を残す**．「〜な人が作った言語」「上司は〜と言った」のように，
  モノではなく人が動いている気配を入れる

| 型 | 例 |
| --- | --- |
| ○ 引用・逆説 | `9. 「プログラミングが大嫌い」な人が作った言語` |
| ○ 言い切り | `10. JSONは発明ではなく「発見」だった` |
| ○ 全角カンマで二節 | `11. ベストバイ3選，1つもPCじゃない` |
| ✕ 二部構成 | `草の下にあった数字──GitHubが『連続記録』を消した日` |
| △ モノが主語 | `Rubyの名前に隠された宝石の秘密` |
| △ 説明的 | `GitHub Copilot Code Review の誤検知が多い理由` |

疑問形は使ってよいが，**疑問形だけで終わらせない**．
「なぜ〜なのか」は入口であって，回の中身は「それを決めた人の話」であるべきである．

## ネタ選びの基準

### 第一関門：人を主語にできるか

**ネタを 1 文で言い直したとき，主語が「人」になるか．**
ならないネタは，採用してよいが優先度を下げる．

- ○「Dan Kaminsky が DNS の欠陥を見つけて，世界中のベンダーを秘密裏に集めた」
- ○「Eric Yuan がビザを 8 回落とされてもアメリカに行こうとした」
- △「DNS キャッシュポイズニングという攻撃手法がある」（主語がモノ）

技術は**その人が何に賭けたかを説明するための道具**として出す．順序を逆にしない．
「何が起きたか」より「**誰がなぜそうしたか**」を軸に据える．

海外の同ジャンルで一番近い Found in the Machine は，全 16 話のほぼ全部に人名が入っている
（Mark Klein，Dan Kaminsky，Hedy Lamarr，David Blackwell，Douglas Engelbart …）．
名前を出せるネタは，それだけで回の背骨になる．

### 探す順番（優先順位）

1. **人物の決断・失敗・執念**（創業者に限らない．メンテナ，標準化委員，内部告発者，最初のユーザー）
2. **裏話**（なぜその仕様になったか，会議室で何が起きたか）
3. **名前の由来・語源**
4. **蘊蓄**（人が出てこない豆知識．単体では弱いので他と束ねる）

いずれも「へー，そうなんだ」と言わせるネタである．
**技術的に踏み込みすぎない**こと．仕様の詳細やコードの話に降りると番組の持ち味から外れる．
一般的なエンジニアが聞いて分かるレベルに保つ．

### ネタの鉱脈：現代の開発者スラングの語源

古典的な由来（Ruby，Docker，Cookie）だけでなく，**今まさに使われている言葉**の出どころを扱う．
YouTube の Etymology Nerd（登録 72.9 万／総再生 6.23 億）は，古語ではなく
**現代のネットスラング**を掘ることでこの規模になっている．
言葉が今変化している現場を扱うと，同時代性が出て刺さりやすい．

例：technical debt（Ward Cunningham），yak shaving，bikeshedding，rubber duck debugging，
cargo cult programming，heisenbug，bus factor，dogfooding，vibe coding，skill issue，
"it works on my machine"，LGTM／nit:／WIP，日本語圏なら「草」「進捗ダメです」．

⚠️ 語源ネタは**由来だけだと 3 分で終わる**．必ず
「その言葉を最初に言った人」「なぜその比喩が選ばれたか」「広まる過程で意味がズレた瞬間」
の 3 点まで掘って，第一関門（人を主語にできるか）を通す．

### 「当たる」ネタの条件

1. **入口が日常**：リスナーが毎日目にしているもの（ステッカー，エラー画面，ロゴ，用語）から入れる
2. **意外な事実が 1 つある**：「え，そうなの？」が言える核がある
3. **人間のドラマがある**：誰がどういう事情でそうしたか，という話に落ちる
4. **裏取りできる**：一次情報が公開されていて，事実として言い切れる
5. **28〜30 分持つ厚みがある**：一次情報が十分にあり，本筋＋寄り道 3〜4 本で 30 分を構成できる．
   事実 1 つで終わるネタは単体で採用せず，関連する事実と束ねて 1 回分にする

避けるもの：単なるニュースの要約，賛否が割れる政治的な話題，一次情報が無い都市伝説を事実として扱うこと（都市伝説そのものを「都市伝説として」扱うのは可）．
